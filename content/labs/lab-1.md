### 1.1 Тема
«Вибір предметної області. Аналіз, моделювання та розроблення адаптивного web-застосунку EduVault».

### 1.2 Мета

### 1.3 Посилання

## 2. Аналіз предметної області

### 2.1 Актуальність теми
У навчальному середовищі матеріали часто зберігаються розрізнено: у месенджерах, хмарних папках, електронній пошті або локально на пристроях студентів. Через це виникають проблеми з пошуком актуальних файлів, повторним використанням конспектів, структурою матеріалів за дисциплінами та контролем доступу.

Вебзастосунок `EduVault` вирішує цю проблему через централізоване зберігання навчальних матеріалів, їх категоризацію, завантаження файлів і розмежування доступу між звичайними користувачами та адміністраторами. Адаптивний інтерфейс є важливим, оскільки користувачі повинні мати змогу працювати з матеріалами як з ноутбука, так і з телефона.

### 2.2 Об'єкт і предмет роботи
**Об'єкт роботи:** процес накопичення, зберігання та використання навчальних матеріалів у цифровому середовищі.

**Предмет роботи:** web-застосунок для керування навчальними матеріалами з підтримкою категорій, користувачів, файлів і ролей доступу.

### 2.3 Практичне значення
Практичним результатом є основа для створення повноцінного backend-проєкту, який можна послідовно розширювати в наступних лабораторних роботах: додати REST API, MySQL, авторизацію, логування, захист, тестування, Swagger та деплой.

### 2.4 Завдання роботи
1. Обрати предметну область для подальшого циклу лабораторних робіт.
2. Сформулювати актуальність теми.
3. Визначити мету, завдання, об'єкт і предмет роботи.
4. Описати бізнес-логіку роботи системи.
5. Сформувати функціональні вимоги до застосунку.
6. Сформувати нефункціональні вимоги до застосунку.
7. Визначити основних акторів системи.
8. Підготувати Use-case діаграму обраної системи.
9. Підготувати ER-діаграму структури даних.
10. Закласти основу для подальшої реалізації web-застосунку.

## 3. Моделювання системи

### 3.1 Актори системи
- **Guest** — переглядає публічну інформацію про сервіс та переходить до авторизації.
- **User** — реєструється, входить у систему, переглядає матеріали, завантажує власні файли.
- **Admin** — модерерує матеріали, керує категоріями, видаляє некоректні або зайві файли.

### 3.2 Бізнес-логіка
1. Користувач проходить реєстрацію та авторизацію в системі.
2. Після входу користувач отримує доступ до списку навчальних матеріалів.
3. Матеріали групуються за категоріями, темами або дисциплінами.
4. Користувач може додати новий матеріал із назвою, описом, категорією та вкладеним файлом.
5. Система зберігає інформацію про файл, автора та дату завантаження.
6. Адміністратор може редагувати або видаляти матеріали, а також керувати категоріями.
7. Для популярних запитів у майбутніх лабораторних роботах застосовується кешування, а доступ до API буде захищений JWT-токенами.

### 3.3 Функціональні вимоги
| ID | Вимога | Опис |
|---|---|---|
| FR-01 | Реєстрація користувача | Система повинна дозволяти створення нового облікового запису. |
| FR-02 | Авторизація користувача | Система повинна дозволяти вхід до особистого кабінету. |
| FR-03 | Перегляд матеріалів | Користувач повинен бачити список доступних матеріалів. |
| FR-04 | Перегляд деталей матеріалу | Система повинна відображати повну інформацію про вибраний матеріал. |
| FR-05 | Додавання матеріалу | Користувач повинен мати змогу завантажити файл і заповнити опис. |
| FR-06 | Категоризація | Матеріали повинні належати до категорій або дисциплін. |
| FR-07 | Редагування та видалення | Адміністратор повинен мати змогу змінювати або видаляти записи. |
| FR-08 | Пошук і фільтрація | Система повинна підтримувати базовий пошук і фільтрацію матеріалів. |

### 3.4 Нефункціональні вимоги
| ID | Вимога | Опис |
|---|---|---|
| NFR-01 | Адаптивність | Інтерфейс повинен коректно відображатися на desktop, tablet і mobile. |
| NFR-02 | Продуктивність | Основні запити мають виконуватися без відчутних затримок для користувача. |
| NFR-03 | Безпека | Доступ до захищених ресурсів повинен виконуватися лише після авторизації. |
| NFR-04 | Масштабованість | Архітектура повинна дозволяти розширення API та БД у наступних лабораторних роботах. |
| NFR-05 | Підтримуваність | Кодова база повинна мати зрозумілу структуру та повторно використовувані модулі. |
| NFR-06 | Надійність | Система повинна обробляти помилки введення та некоректні запити без аварійного завершення. |

### 3.5 Use-case діаграма
Для системи `EduVault` доцільно виділити такі основні сценарії:
- реєстрація користувача;
- авторизація користувача;
- перегляд списку матеріалів;
- перегляд конкретного матеріалу;
- завантаження нового матеріалу;
- керування категоріями;
- модерація та видалення матеріалів адміністратором.

Графічна Use-case діаграма буде додана до звіту після побудови схеми у diagrams.net або іншому UML-інструменті.

### 3.6 ER-модель даних
Попередньо для системи доцільно виділити такі сутності:
- **User** — користувач системи;
- **Role** — роль користувача;
- **Category** — категорія або дисципліна;
- **Material** — навчальний матеріал;
- **FileAsset** — метадані завантаженого файлу.

Базові зв'язки:
- один користувач може мати багато матеріалів;
- одна категорія може містити багато матеріалів;
- один матеріал має один пов'язаний файл;
- одна роль може належати багатьом користувачам.

ER-діаграма буде додана у графічному вигляді на наступному етапі оформлення звіту.

## 4. Концепція інтерфейсу застосунку

### 4.1 Основні сторінки
- головна сторінка з описом сервісу;
- сторінка входу та реєстрації;
- каталог навчальних матеріалів;
- сторінка перегляду конкретного матеріалу;
- форма завантаження нового матеріалу;
- адміністративна панель для керування матеріалами та категоріями.

### 4.2 Адаптивність
Інтерфейс повинен коректно працювати на різних розмірах екрана. Для цього передбачається:
- адаптивна навігація;
- компактне меню для мобільних пристроїв;
- зручне відображення карток матеріалів на малих екранах;
- читабельна типографіка та достатні відступи.
